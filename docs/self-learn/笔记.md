grep 和 ripgrep差别是？

要区分 **系统命令** `grep` 和 **DeepSeek Harness 的** `grep` **工具**。

如果比较两个命令行程序：


|                 | `grep`          | ripgrep（`rg`） |
| --------------- | --------------- | ------------- |
| 用途              | 搜索文本，常用于文件或管道输入 | 搜索文本，尤其适合代码仓库 |
| 搜索子目录           | 通常需要 `-r`       | 默认递归          |
| 遵守 `.gitignore` | 默认不遵守           | 默认遵守          |
| 隐藏文件            | 递归时通常会搜索        | 默认跳过          |
| 性能              | 适合一般文本处理        | 搜索大型代码库通常更快   |


```
grep -rn "signIn" src/
rg -n "signIn" src/

```

两条命令都可以搜索 `src/` 下的文本，但默认过滤规则不同，结果可能不完全相同。

**在 DeepSeek Harness 里，**`grep` **只是模型看到的工具名称，底层实际使用的是 ripgrep，并不是调用系统的** `grep` **命令。**

```
  Worked for 15s • 20:42

```

ripgrep 这是个工具包是吧

对，更准确地说，**ripgrep 是一个独立的命令行工具**，安装后用 `rg` 命令调用，由 Rust 编写。

DeepSeek Harness 把它作为底层搜索程序，再封装成模型可以调用的 `grep`、`glob` 工具：

```
模型调用 grep / glob → Harness 调用 ripgrep → 返回搜索结果

```

什么时候会调用 glob、grep？

**主要是在模型判断“需要查找本地文件或代码”时调用**，不是每条消息都会自动搜索。

例如：


| 你的问题或任务                  | 模型可能采取的操作                     |
| ------------------------ | ----------------------------- |
| “登录页面在哪个文件？”             | 用 `glob` 找 `**/*login*` 等文件路径 |
| “哪里用了 `searchSessions`？” | 用 `grep` 搜这个标识符               |
| “这个报错是哪里抛出的？”            | 用 `grep` 搜错误文本，再读取附近代码        |
| “解释这个项目的搜索实现”            | 找相关文件、搜索函数，再读取源码              |
| “修改这个函数”                 | 先定位并读取代码，必要时搜索调用方             |


典型流程是：

```
用户提出问题
    ↓
模型根据问题和已有上下文，判断缺少哪些代码信息
    ↓
调用 glob 找文件 / grep 搜内容
    ↓
Harness 执行 ripgrep，将结果返回模型
    ↓
模型调用 read 读取相关代码
    ↓
回答问题，或继续修改代码

```

`glob`**、**`grep`**、**`read` **不要求固定顺序。** 已知文件路径可以直接 `read`；已知函数名可以直接 `grep`；搜索结果足够回答时，也不必继续读取。

```

   ↓
```

SQLite FTS5 全文索引 是什么？ FTS 是？

**FTS 是 Full-Text Search 的缩写，中文叫“全文搜索”；FTS5 是 SQLite 的全文搜索模块，第 5 代实现。**

它让你能够快速搜索数据库里存储的大段文字，例如文章、聊天记录、文档。

普通查询可以这样写：

```
SELECT * FROM messages WHERE content LIKE '%数据库%';

```

这种包含匹配通常需要逐条检查文本。FTS5 则提前把文本拆成词项，建立**倒排索引**，记录“哪个词出现在哪些记录中”，搜索时直接通过索引找到记录。

例如：

```
记录 1：SQLite 支持全文搜索
记录 2：Harness 使用 SQLite 保存会话

索引大致是：
SQLite → 记录 1、记录 2
Harness → 记录 2
全文搜索 → 记录 1

```

实际如何拆词取决于配置的分词器，上面只是示意。

SQLite 中可以这样使用：

```
-- 创建全文搜索表
CREATE VIRTUAL TABLE messages USING fts5(content);

-- 写入文本，索引随之维护
INSERT INTO messages(content) VALUES ('Harness uses SQLite');

-- 搜索包含 SQLite 这个词的记录
SELECT * FROM messages WHERE messages MATCH 'SQLite';

```

在 DeepSeek Harness 中，它用于**检索历史会话内容**。它属于基于词项的文本检索，**不是 embedding 向量检索**：搜索“汽车”不会天然匹配只写了“轿车”的内容。

在 `packages/session-query/session-query-sqlite/` 模块，包名是 `@deepseek-ai/dsh-session-query-sqlite`。

主要看这三个文件：


| 文件                                                                                  | 负责什么                                                                                                                              |
| ----------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `src/schema.ts:127` (packages/session-query/session-query-sqlite/src/schema.ts:127) | 创建 FTS5 索引表：持久化记录 `persisted_docs` 和临时的实时记录 `live_docs`，使用 `unicode61` 分词器                                                        |
| `src/index.ts` (packages/session-query/session-query-sqlite/src/index.ts)           | 会话搜索服务、索引维护和查询执行；第 819 行 (packages/session-query/session-query-sqlite/src/index.ts:819)附近通过 `WHERE persisted_docs MATCH ?` 执行全文搜索 |
| `src/query.ts` (packages/session-query/session-query-sqlite/src/query.ts)           | 搜索参数处理、查询条件构造、FTS 文本转义和结果摘要处理                                                                                                     |


注意：**FTS5 搜索引擎本身由 SQLite 提供**；这个模块通过 Node 的 `node:sqlite` 使用它，负责将 Harness 的会话数据建立索引并提供查询能力



这里的调用是**本地服务调用 → SQLite 执行全文搜索 → 返回匹配的会话记录**，不需要请求外部搜索 API。

```
Web 界面的会话搜索 / 可选的模型会话查询工具
                     ↓
          ctx.sessionQuery.searchSessions()
                     ↓
          session-query-sqlite 实现
                     ↓
          校验搜索参数、准备数据库
                     ↓
          检查会话变化，更新搜索索引
                     ↓
          SQLite 执行 FTS5 MATCH 查询
                     ↓
          过滤、排序、生成摘要和分页
                     ↓
          返回界面或模型工具

```

具体可以按下面顺序读代码：

**1. 调用搜索服务**

Web 的会话搜索在 `session-controller/src/list.ts:236` (packages/api/session-controller/src/list.ts:236) 调用 `searchSessions()`。

可选的模型查询工具在 `tool-session-query/src/operations.ts:95` (packages/experimental/tool-session-query/src/operations.ts:95) 调用：

```
ctx.sessionQuery.searchSessions({
  query,
  sessionFilters,
  eventFilters,
}, { signal })

```

其中 `query` 是搜索文本，其他参数用于限制会话、事件范围和取消请求。

**2. 搜索实现先同步索引**

`session-query-sqlite/src/index.ts:268` (packages/session-query/session-query-sqlite/src/index.ts:268) 的 `searchSessions()` 依次执行：

```
normalizeSessionRequest()   规范化参数
_serialized()              将操作排队执行
_ensureReady()             确保数据库就绪
_reconcile()               将索引与当前会话数据同步
_querySessions()           执行查询
page()                     整理分页结果

```

`_reconcile()` 会检查新增、修改、删除的会话并更新索引，**不是每次都重建全部索引**。

**3. SQLite 真正执行全文匹配**

在 `index.ts:819` (packages/session-query/session-query-sqlite/src/index.ts:819) 附近，核心 SQL 是：

```
WHERE persisted_docs MATCH ?

```

实时会话则搜索：

```
WHERE live_docs MATCH ?

```

`?` 通过参数绑定传入处理后的搜索文本。**分词和倒排索引查找由 SQLite FTS5 完成**。同一个会话如果有实时版本，会优先使用实时数据，避免同时返回旧的持久化版本。

**4. 整理并返回结果**

查询会应用过滤条件，并按匹配次数、文本长度、时间等排序。`searchSessions()` 为每个会话选一个代表性命中，生成摘要和分页游标，再返回调用方。

另一个入口 `searchEvents()` 流程类似，但用于**搜索指定会话内的事件**，而不是跨会话找结果。



是什么数据会存进persisted_docs 的？

`persisted_docs` **存的是“从已持久化会话日志中提取出来的可搜索文本”，不是原始日志，也不是整个代码仓库。**

哪些内容会进去，由 `extraction.ts` (packages/session-query/session-query/src/extraction.ts:16) 决定：


| 会话事件                | 提取的内容                                       |
| ------------------- | ------------------------------------------- |
| `user/message`      | 用户消息中的文本                                    |
| `assistant/message` | 助手消息中的文本，以及工具调用块中的名称和参数                     |
| `tool/call`         | 工具名称、调用参数                                   |
| `tool/result`       | 工具返回的文本、错误名称和错误码                            |
| `todo/write`        | 待办事项的状态和内容                                  |
| `turn/end`          | 异常结束信息，如错误消息、`aborted`、`max-tokens`；正常完成不提取 |


**不会写入的内容**包括 reasoning 块、图片等非文本块、原始流数据、请求头、步骤开始/结束等结构性事件，以及尚未定义提取规则的事件。

每个提取出非空文本的事件，会生成一条搜索文档。例如：

```
用户消息：帮我查一下 SQLite
        ↓
persisted_docs 中的一行：
text             = "帮我查一下 SQLite"
session_id       = 所属会话 ID
seq              = 事件序号
type             = "user/message"
time             = 事件时间
surface          = current / shadowed / log-only
codepoint_length = 文本字符数

```

其中 **只有** `text` **建立全文索引**，其余字段保存为元数据，用于定位、过滤和排序。`surface` 区分当前对话内容、被替换的历史内容，以及仅存在于日志中的事件。

对应的数据路径是：

```
已持久化的会话事件
    ↓ extractSessionEventText()
提取可搜索文本
    ↓ buildSessionEventSearchDocuments()
补充会话 ID、事件序号等元数据
    ↓ _replacePersistedSession()
写入 persisted_docs，SQLite 自动维护全文索引

```

生成文档见 `documents.ts:36` (packages/session-query/session-query/src/documents.ts:36)，写入数据库见 `index.ts:582` (packages/session-query/session-query-sqlite/src/index.ts:582)。

所以，**网页内容或文件内容只有作为工具结果文本记录进会话日志后，才会通过这条路径进入索引**；这个模块不会主动扫描所有网页或本地文件。
