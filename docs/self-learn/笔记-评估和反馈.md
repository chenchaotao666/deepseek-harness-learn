**1. 用户反馈：已经有明确实现**

反馈分为两个独立层级：


| 层级              | 入口                                            | 记录内容          |
| --------------- | --------------------------------------------- | ------------- |
| 整个会话            | `/feedback`、Web 反馈弹窗、`sessionFeedback` Remote | 文本评价、分类等      |
| 单条 assistant 消息 | 消息反馈 UI、`messageFeedback` 服务                  | 好评/差评、可选分类和备注 |


底层使用 Session 事件保存：

```
feedback/record          会话反馈
feedback/message-put     新增或修改消息反馈
feedback/message-delete  撤回消息反馈

```

消息反馈支持读取、修改和删除当前反馈。不过，删除通过追加事件实现，旧评分和备注仍保留在历史日志中，**不等于隐私擦除**。

最关键的设计是：**这些反馈只进入日志，不进入模型上下文，也不启动或打断模型工作。** 因此，“点差评”和“在对话里要求模型修正回答”是两种不同操作。

源码入口：反馈包组 (packages/feedback/[README.zh.md](http://README.zh.md))、消息反馈实现 (packages/feedback/message-feedback/src/index.ts)。

**2. 评估：工程验证比较完整**

仓库提供多层验证：

- **单元测试**：检查接口行为、错误路径、并发和生命周期。
- **真实 API e2e**：验证真实模型及相关提供方接入。
- **记录会话回放**：用记录好的模型响应重放流程，比较持久化结果和工作区输出。
- **浏览器快照**：检查用户界面的行为及呈现。
- **性能基准**：约束耗时、内存和规模增长表现。

其中，**回放测试验证的是已有场景有没有回归，不等于测量模型面对新任务的成功率**；代码覆盖率也不等于回答质量评分。

详见 测试策略 (docs/[testing.zh.md](http://testing.zh.md))。

**3. 运行时审查：有实验性的 Auto review**

启用后，当前 agent 使用的模型会在原生工具调用或 PTC 内部工具调用之前评估待执行动作：

```
待执行工具调用
    ↓
模型审查
    ├── 获准：放行执行
    └── 被拒绝：请求用户审批

```

这是工具动作审查，不是给最终回答评分。该能力默认关闭，可能误放行或误拒绝，也会消耗额外 token。见 Auto review 说明 (packages/experimental/auto-review/[README.zh.md](http://README.zh.md))。

当前怎么使用用户反馈的feedback内容？有使用么

**有使用，但目前主要用于记录与遥测导出，没有直接用于让 Agent 自动改进。**

根据当前仓库实现，反馈内容的去向是：

```
用户提交评价、评分、分类或备注
    ↓
写入 Session 日志
    ├── 界面读取：展示当前评分，支持修改和撤回
    └── 遥测导出：按部署配置导出反馈及相关会话日志

```

具体分为三部分：


| 用途                     | 当前情况                       |
| ---------------------- | -------------------------- |
| 保存反馈                   | 已实现，以 Session 事件持久化        |
| 界面展示与管理                | 消息评分支持读取、修改、撤回             |
| 遥测导出                   | 已有 OTel 导出策略，是否实际发送取决于部署配置 |
| 反馈自动进入模型上下文            | **不会**                     |
| 根据差评自动重答、修改 Skill 或提示词 | 当前查阅范围内未发现                 |
| 自动训练、统一评分分析或改进闭环       | 当前查阅范围内未发现                 |


一个关键细节是：随附 OTel 后端在 `FEEDBACK_ONLY` 模式下，会在新的显式反馈、评分编辑或撤回后，释放对应的**完整权威会话日志前缀**供导出，其中包含上下文和备注；`DISABLED` 模式阻止捕获。因此反馈不仅可以作为一个评分，还能关联当时的对话，供后续分析。具体见 消息反馈说明 (packages/feedback/message-feedback/[README.zh.md](http://README.zh.md))。

但**仓库支持导出，不代表我已经确认你的部署启用了导出，也不能据此断言服务端正在拿它训练模型**。

所以，如果你问的是“用户反馈有没有被 Agent 消费”：**没有直接消费。** 用户点差评不会影响下一次模型请求；要让当前 Agent 修正，需要在对话中明确指出问题。当前反馈系统更多提供了采集和分析所需的数据基础。

| 测试     | 核心问题                      |
| ------ | ------------------------- |
| 记录会话回放 | 给定相同模型响应，系统执行结果有没有变化？     |

它们都有**准备输入 → 执行真实代码 → 获取结果 → 与预期比较**的过程，但输入和判定标准不同。

**1. 记录会话回放：固定模型响应，重新执行系统**

模型每次实时回答可能不同，不适合直接作为确定性回归测试。因此仓库先记录一次模型交互，再在测试中重放这些响应。

场景一般包含：

```
某个场景/
├── snapshot.yml         场景配置：profile、组合、记录策略等
├── session.vN.jsonl      已记录会话
├── workspace.expected/  工具执行后的预期工作区（适用时）
└── 其他预期输出

```

其中会话 JSONL 同时提供回放输入和预期持久化结果。

执行过程：

```
读取场景配置和记录会话
    ↓
准备隔离的临时工作目录与输入文件
    ↓
通过 dsh CLI 启动指定 profile
    ↓
输入已记录的用户任务
    ↓
回放适配器返回已记录的模型响应
    ↓
真实运行工具、事件处理和会话持久化
    ↓
比较请求、会话日志及场景声明的外部输出

```

例如，记录中的模型要求：

```
读取 README → 写入 summary.md → 回复“完成”

```

回放时不用再问真实模型“接下来做什么”，但文件读取和写入流程仍需要执行。测试既比较会话结果，也可以比较最终 [`summary.md`](http://summary.md) 的内容。

**不能只检查模型回复“文件已写入”。** 对修改工作区的场景，仓库要求独立比较整个预期工作区；录制和刷新不会自动改写 `workspace.expected/`，避免把错误副作用直接接受为新答案。

为消除随机差异，测试会规范化会话 ID、时间等易变内容，同时保留 ID 之间的关联关系；不会随意删除业务文本来掩盖差异。

仓库区分三个模式：


| 模式        | 行为                     |
| --------- | ---------------------- |
| `replay`  | 默认模式，无需模型密钥，只比较，不改预期文件 |
| `record`  | 调用真实模型，重新记录响应和预期输出     |
| `refresh` | 使用已有模型响应，刷新当前执行产生的预期输出 |


对应脚本是 `test:snapshot`、`test:snapshot:record`、`test:snapshot:refresh`。预期文件变化仍需人工审阅。

入口：vitest.snapshot.config.ts (vitest.snapshot.config.ts)、headless.snapshot.ts (snapshots/session/headless.snapshot.ts)。

**它的限制：**能够发现工具行为、日志结构、上下文组装等回归，但不能证明新模型面对新问题仍能选择正确工具。

**2. 浏览器快照：真实操作浏览器，比较页面状态**

这里需要澄清：**仓库的浏览器快照不全是 PNG 截图比较。** 很多场景保存的是页面的 ARIA 可访问性结构，并结合交互、DOM 或几何断言。

例如实际的快照内容包括：

```
- status: Completed
- button "Searched the web" [expanded]
- paragraph: SEARCH_DONE
- button "Good response"
- button "Bad response"
- textbox "Message or run a task, / commands, @ files or sessions"
- button "Send message" [disabled]

```

这种文本描述页面里有哪些控件、它们的名称和状态，容易在代码审查中比较。

基本过程：

```
构建客户端资源
    ↓
启动测试宿主与浏览器
    ↓
准备会话或回放固定模型交互
    ↓
通过 Playwright 点击、输入、切换视图等
    ↓
等待明确的 UI 状态
    ↓
提取 ARIA 快照或执行专项断言
    ↓
与提交到仓库的 expected 文件比较

```

例如测试工具调用展示：

1. 用户提交任务。
2. 模型回放返回工具调用。
3. 工具执行，页面出现工具卡片。
4. 点击展开卡片。
5. 比较名称、展开状态、结果文本及最终回答。

它能发现：

- 应出现的按钮消失。
- 按钮名称或可访问性标签错误。
- 发送按钮的启用状态不对。
- 工具卡片没有展开或没有更新。
- 点击后产生了错误的界面状态。

**ARIA 快照不能证明颜色、间距和布局都正确。** 这些需要对应的几何断言、截图或渲染检查；不能把文本快照通过等同于完整视觉验证。

会话驱动的场景放在 `snapshots/web/`，纯 UI 预期输出放在 `apps/web/tests/expected/`。仓库主要使用 Chromium，部分选择器场景还覆盖 WebKit。

入口：vitest.web.config.ts (vitest.web.config.ts)、实际 UI 预期文件 (snapshots/web/web-search-round/[ui.expected.md](http://ui.expected.md))。

运行入口为 `pnpm run test:web`；CI 比较既有预期文件，刷新是显式操作。

**3. 性能基准：固定工作负载，多次采样，与预算比较**

性能测试不比较“答案文本”，而是测量一个明确用户路径的资源消耗。

例如当前的会话打开基准会构造：

```
200 轮对话
127,400 个事件

```

然后测量历史会话首次打开、升级后重新打开、首次历史读取、agent 恢复等路径。

执行过程：

```
按固定常量生成合成数据
    ↓
构建产品库和 benchmark worker
    ↓
在新的子进程中运行指定路径
    ↓
记录耗时、CPU、内存等指标
    ↓
重复采样，计算中位数等统计值
    ↓
与预算比较，生成报告

```

这个会话打开案例使用 5 次新进程采样，并通过中位数判断相应耗时预算。它也单独设置受限堆内存场景。

测量通常分为三类：


| 指标   | 判定方式示例                |
| ---- | --------------------- |
| 耗时   | 打开或恢复耗时的中位数不能超过预算     |
| 内存   | 保留堆内存或进程峰值 RSS 不能超过预算 |
| 规模增长 | 大输入相对小输入的耗时增长比不能超过上限  |


“规模增长”用于发现算法退化。例如，输入扩大后耗时增长远超预期，即使小输入仍很快，也可能暴露重复扫描或近似平方复杂度的问题。仓库的 conversation-fold 基准同时检查耗时与增长比例。

为减少测量污染，仓库要求：

- 使用固定合成数据，不依赖用户会话、环境仓库或网络服务。
- 进程级样本使用新子进程和独立临时目录。
- 计时中的 CPU 工作运行在构建后的普通 Node worker 中，不通过 TSX 加载产品代码。
- 记录测量范围、原始样本和统计方式。
- 时间预算考虑参考机器与 CI 差异；内存和无量纲比例不套用时间缩放系数。

测试生成 `.dsh-report/report.html`，CI 发布为 `benchmark-report` artifact。

入口：session-open.bench.ts (benchmarks/session-open/session-open.bench.ts)、conversation-fold.bench.client.ts (benchmarks/conversation-fold/conversation-fold.bench.client.ts)、基准规则 (benchmarks/[AGENTS.md](http://AGENTS.md))。

运行入口为 `pnpm run test:bench`，会先构建所需资源。性能失败说明测量结果超过预算，需要结合样本和环境诊断；不一定能仅凭一次超时就认定算法退化。
